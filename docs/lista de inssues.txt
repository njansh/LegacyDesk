# Milestone: MVP 1 — Sistema de Gestão de Serviços

**Objetivo:** criar um sistema de gestão de solicitações utilizado por funcionários de uma empresa, permitindo registrar clientes, abrir solicitações, atribuir técnicos, acompanhar o atendimento e manter histórico e auditoria.

**Restrições do projeto:**

* Java 8
* Spring Boot 2.7.x
* Maven
* PostgreSQL
* Docker
* API REST
* arquitetura modular
* sem utilizar recursos exclusivos de versões modernas do Java
* resolver problemas modernos utilizando ferramentas disponíveis nessa stack

### #14 Implementar autorização por função

O sistema deve impedir acesso a funcionalidades incompatíveis com a função do usuário.

Isso é particularmente importante porque **autenticação não significa autorização**. A OWASP classifica autorização quebrada em nível de objeto e de função entre os principais riscos de APIs. ([Guia do Desenvolvedor OWASP][2])

---

### #15 Implementar controle de acesso por recurso

Não basta verificar:

> "o usuário está logado?"

Também precisamos verificar:

> "esse usuário pode acessar **este recurso específico**?"

Exemplo:

```text
GET /requests/123
```

O fato de o usuário conseguir acessar `/requests/123` não significa automaticamente que ele pode visualizar aquela solicitação.

Isso nos coloca diretamente diante de BOLA/IDOR. ([OWASP][3])

# 12. Segurança e vazamento de dados

Aqui eu colocaria uma **milestone própria**, porque é uma parte importante do nosso exercício.

### #42 Definir dados sensíveis

Identificar quais informações:

* podem ser retornadas;
* precisam de autorização;
* nunca devem aparecer na API;
* nunca devem aparecer nos logs.

---

### #43 Implementar proteção contra exposição excessiva

As respostas da API não devem simplesmente serializar entidades inteiras.

Precisamos retornar **somente o necessário para aquele contexto**.

A OWASP chama atenção especificamente para esse problema: APIs que retornam propriedades além das necessárias podem expor PII, tokens, identificadores internos e outras informações sensíveis. ([OWASP][4])

---

### #44 Implementar proteção contra Mass Assignment

O cliente não poderá enviar propriedades que não deveria controlar.

Por exemplo, uma requisição de atualização não pode simplesmente permitir que alguém envie:

```text
role=ADMIN
```

ou alguma propriedade interna equivalente.

---

### #45 Revisar mensagens de erro

Erros não devem revelar:

* stack trace;
* SQL;
* estrutura interna;
* credenciais;
* tokens;
* informações desnecessárias do banco.

---

### #46 Revisar logs

Garantir que informações sensíveis não sejam registradas.

---

### #47 Testar vazamento de dados

Criar testes tentando descobrir se:

* um funcionário consegue acessar dados indevidos;
* um usuário consegue acessar outro recurso;
* uma resposta contém campos sensíveis;
* propriedades internas podem ser alteradas;
* erros revelam informações internas;
* logs armazenam dados que não deveriam.

Isso vai transformar segurança em algo que você **tenta quebrar**, e não simplesmente uma configuração. A OWASP inclusive trata testes de acesso cruzado entre identidades como uma forma importante de verificar autorização em nível de objeto. ([OWASP][5])

# 14. Processamento assíncrono

### #51 Implementar operação assíncrona

Uma operação que não precisa bloquear a criação da solicitação deverá ser executada de forma assíncrona.

E aqui temos uma restrição interessante:

**não quero que você resolva isso automaticamente com uma API moderna.**

Java 8 possui suas próprias ferramentas de concorrência, então você terá que entender o problema antes de escolher a solução.

---

### #52 Tratar falhas do processamento assíncrono

Precisamos descobrir:

> O que acontece se a operação assíncrona falhar?

Não podemos simplesmente ignorar a exceção.

---

# 15. Idempotência

### #53 Identificar requisições duplicadas

Precisamos impedir que uma mesma operação enviada duas vezes provoque efeitos duplicados.

Exemplo:

```text
POST /requests
```

O cliente envia duas vezes por causa de uma falha de rede.

O sistema deve conseguir reconhecer que aquilo representa a mesma operação.

---

### #54 Testar idempotência

Testar:

* requisição repetida;
* timeout;
* retry;
* envio simultâneo.
